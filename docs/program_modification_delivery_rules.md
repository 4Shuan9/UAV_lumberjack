# 程序修改与交付规则

以后帮我修改程序时，请严格按下面的方式交付，不要每次都给我整包，也不要只告诉我“改哪里”。

## 1. 小改动：直接给修改指令

如果只是改几行参数、变量、小段逻辑、字符串或增加一个很小的判断，请直接给我可以复制执行的终端命令，或者明确告诉我“找到哪一段、替换成什么”。

例如：

```bash
sed -i 's/old/new/' xxx.cpp
```

这种小修改不要生成补丁包。

## 2. 单个文件大幅修改：给完整替换文件

如果一个文件需要大量修改、重构较多逻辑、增加较多函数、修改位置较散，或者用 sed/局部替换容易出错，请直接输出完整修改后的文件让我覆盖原文件。

不要只给 diff，也不要让我自己拼很多代码段。

交付时明确告诉我：

```text
替换文件：
~/项目路径/xxx.cpp
```

## 3. 多个文件修改：给补丁包

如果一次修改涉及多个文件，例如：

- cpp + hpp
- cpp + yaml
- launch + config + source
- 多个 ROS 2 package
- 新增文件同时修改旧文件

请直接整理成一个 zip 补丁包。

补丁包内部目录结构必须和项目原目录对应，例如：

```text
patch/
└── ros2_ws/
    └── src/
        └── xxx_package/
            ├── src/
            │   └── xxx.cpp
            └── config/
                └── xxx.yaml
```

最好同时附一个简短 README，写清楚：

- 修改了哪些文件
- 为什么改
- 怎么覆盖
- 是否需要重新编译
- 修改后如何验证

## 4. 整项目整理：给完整项目包

如果任务是合并工程、重组目录、清理冗余文件、调整多个 ROS 2 package 与仿真资源，或者统一 README/docs/sim/ros2_ws 等，请直接输出整理后的完整项目包。

不要只给目录建议，也不要让我手工移动几十个文件。

## 5. 总体交付原则

```text
小工作
→ 直接给修改指令

单文件大改
→ 给完整替换文件

多文件修改
→ 给补丁包

整项目整理
→ 给完整项目包
```

除非我明确要求，否则不要因为一个小 bug 给我整包工程，也不要在单文件大改时只给零散代码片段。

## 6. 代码修改原则

1. 以我最新提供的源码为准。
2. 如果拿不到当前最新源码，直接让我重新上传，不要根据旧版本猜。
3. 不要顺手大改和当前问题无关的部分。
4. 尽量保留我已有的节点名、topic、action/service 接口、参数名、launch 方式和状态机结构。
5. 修问题时先定位原因，再做最小必要修改。
6. 如果只是诊断性参数调整，要明确告诉我是临时验证参数还是最终方案。
7. 修改后必须告诉我：改了什么、为什么、怎么编译、怎么运行、看什么现象判断成功。

## 7. 调试任务的工作方式

我不喜欢一上来就“一键全自动重构整个工程”。

我更习惯：

```text
先分析问题
↓
解释原因
↓
一步一步定位
↓
确认问题
↓
再修改
```

所以调试任务优先逐步定位，不要一上来重构整个项目。能通过小改验证的问题，先做最小验证；验证成立后，再决定最终修改方案。

## 8. 文件真实性要求

只要修改依赖源码内容：

- 必须以当前最新文件为准
- 不要根据过去对话中的旧代码直接生成新版本
- 不要凭印象补不存在的函数、参数或接口
- 如果文件已过期、缺失或不可访问，就直接让我重新上传
- 如果我刚贴了最新代码片段，则优先以我刚贴出的内容为准

## 9. ROS 2 / 工程修改时的额外要求

如果是 ROS 2 项目，尽量不要随意改变已有：

```text
package name
node name
topic name
service name
action name
parameter name
launch entry
workspace structure
```

除非当前问题本身就需要修改这些接口。

修改后给出最短可执行流程，例如：

```bash
cd ~/project/ros2_ws
source /opt/ros/humble/setup.bash
colcon build --packages-select xxx --symlink-install
source install/setup.bash
ros2 launch ...
```

不要只说“重新编译运行”。

## 10. 我的偏好

我的工作习惯是：先理解原理，再一步一步做实验；真正需要修改代码时，再给我可以直接用的结果。

回答时优先：

1. 先告诉我问题在哪里
2. 再告诉我为什么
3. 再给最小验证方法
4. 最后按照修改规模决定交付形式

不要默认我希望一键自动完成所有配置。

## 11. 一句话规则

```text
小改给命令，
单文件大改给完整文件，
多文件改给补丁包，
整项目整理给完整项目包；
始终以最新源码为准，先定位再修改，不要无关重构。
```
